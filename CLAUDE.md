# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Raspberry Pi Pico 2 W (RP2350) firmware that bridges a Sony DualSense (DS5) controller over Bluetooth Classic to a USB host. Presents itself to the host as a USB HID + UAC1 audio composite device. This repo is `MarcelineVPQ/DS5Dongle-OLED-Edition`, a personal fork of upstream `awalol/DS5Dongle` that adds an optional Waveshare Pico-OLED-1.3 status display (10 screens) and a 4-slot persistent multi-controller pairing layer.

`README.md` is authoritative for user-facing capability; `CHANGELOG.md` tracks what shipped per release. Read both before proposing changes — much of the design is non-obvious from the code alone (audit history, BT pairing-posture rationale, clock and flash setup history).

## Build

Verification is hardware-in-the-loop (see "Hardware-in-the-loop workflow" below). The pure logic also has host unit tests: `tests/host/run.sh` builds `src/{calib,remap,config,cmd,perf,ctrl_info,dse}.cpp`, the USB suspend / wake state machine (`src/usb_power.h`) and the OLED flush / Status-screen controller glyph (`src/oled_pad.h`, mirror symmetry) / title scroll (`src/title_scroll.h`) / stick-curve / firmware-report 0x20 (`src/fw_report.h`) / haptics decimation (`src/haptics_decimate.h`, checked against WDL itself) / mono-speaker-to-headset detection (`src/speaker_mono.h`) / OLED KEY0/KEY1 press logic and remote presses (`src/oled_keys.h`) / the app's virtual controller buttons for the OLED (`src/oled_vpad.h`) / the Bluetooth inquiry policy (`src/scan_policy.h`) / the Status screen without a controller and its pairing countdown (`src/pair_prompt.h`) / the status line on every OLED screen (`src/oled_toast.h`) / the mic jitter buffer's level control (`src/mic_level.h`, with a latency simulation) headers on the PC against SDK stubs (`tests/host/stubs/`, flash is a RAM array in `fakes.cpp`) with ASan + UBSan, no hardware; CI runs it. Add a test there when you change that logic. `tools/analyze.sh [build dir] [--tidy] [--cppcheck]` prints section sizes, the RAM image split (libopus / other `.time_critical` / variables), the biggest RAM and flash symbols, the deepest stack frames (configure with `-DENABLE_STACK_USAGE=ON`) and clang-tidy / cppcheck findings over our `src/` (`tools/analyze.sh --install` puts both tools into `~/.cache/ds5dongle/tools/venv`, no root).

The build is **non-trivial to set up** because it requires a specific Pico SDK, TinyUSB and compiler. The pins live in one file, `tools/toolchain.env` (CI loads it; `tools/dev_firmware.sh` and `tools/release.sh` warn when a local setup differs, via `tools/toolchain.sh`): **Pico SDK 2.3.0, TinyUSB at upstream's commit 2d56dc5 (0.21 + hathach/tinyusb#3758), ARM GNU Toolchain 15.2.Rel1** (as upstream awalol 994f310 / 898c352; upstream's fix for DualSense V2 CFI-ZCT2W reconnect failures and watchdog reboot loops, #235). CMake refuses any TinyUSB other than 0.21, because the `relocate_to_ram()` section names are 0.21's. **`tools/install_toolchain.sh`** sets up a local build like CI's in one go: the pinned toolchain into `~/.local/opt/arm-gnu-toolchain-<version>` (which `tools/toolchain.sh` then uses by default) and `~/pico-sdk` (or `$PICO_SDK_PATH`) at the pinned SDK and TinyUSB.

```bash
# Pico SDK 2.3.0 with TinyUSB at the pinned commit. The SDK still bundles
# TinyUSB 0.18.0, which lacks the 4-arg TUD_AUDIO_EP_SIZE in src/tusb_config.h;
# the pin is 0.21.0 plus hathach/tinyusb#3758 (rp2040 dcd fixes among others).
# Any folder works; point PICO_SDK_PATH at it (the system SDK can stay as is).
git clone --depth 1 --branch 2.3.0 https://github.com/raspberrypi/pico-sdk.git ~/sdk23/pico-sdk
git -C ~/sdk23/pico-sdk submodule update --init --recursive
git -C ~/sdk23/pico-sdk/lib/tinyusb fetch --depth 1 origin 2d56dc533e45e4e91b15e93fdab5e22e964f328d
git -C ~/sdk23/pico-sdk/lib/tinyusb checkout --detach FETCH_HEAD
# ARM's toolchain: the tarball at ARM_TOOLCHAIN_URL in tools/toolchain.env,
# unpacked anywhere (e.g. ~/sdk23/arm-toolchain, the folder holding bin/).
export PICO_SDK_PATH=~/sdk23/pico-sdk PICO_TOOLCHAIN_PATH=~/sdk23/arm-toolchain

# Build (tools/dev_firmware.sh does this with the same two variables)
cd /path/to/DS5Dongle
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DPICO_SDK_PATH="$PICO_SDK_PATH"
cmake --build build --target ds5-bridge
# Produces build/ds5-bridge-oled.uf2  (output name set in CMakeLists.txt, not the default)
```

Common build flags (set via `-D` on the cmake invocation):

- `ENABLE_SERIAL=ON` — route printf to USB CDC for debugging. Default OFF (production).
- `ENABLE_VERBOSE=ON` — chatty BT/HID logging. Default OFF.
- `ENABLE_BATT_LED=OFF` — disable the low-battery LED blink. Default ON.
- `PICO_W_BUILD=ON` — build for the original Pico W (drops audio, lower clock). Default targets Pico 2 W.
- `DS5_CLOCK_KHZ=320000` — Pico 2 W only: the old overclock (1.20 V, CYW43 PIO divider 5, boot2 flash divider 4), kept for one release as a fallback; then remove it. Default `150000` (stock). Any other value is a configure error.
- `OPUS_ENCODER_CELT_ONLY=OFF` — speaker encoder back to `OPUS_APPLICATION_AUDIO`. Default ON = `OPUS_APPLICATION_RESTRICTED_CELT` (libopus 1.6): at our settings (48 kHz stereo, 10 ms, 160 kbps CBR, complexity 0) AUDIO already sends only CELT full-band 10 ms stereo packets (TOC 0xF4, 200 bytes), so the controller gets the same kind of packet, from ~24 KB less encoder heap (48.7 → 24.4 KB) and with 4 ms less look-ahead.
- `ENABLE_STACK_USAGE=ON` — `-fstack-usage` on our code, libopus and the resampler, for `tools/analyze.sh`.
- libopus is built with `OPUS_HARDENING`, `OPUS_STACK_PROTECTOR` and `OPUS_FORTIFY_SOURCE` **off** (forced in CMakeLists.txt): fortify turned its `memcpy`/`memset` into `__memcpy_chk`/`__memset_chk` in flash, so core1 left RAM every frame, and hardening's asserts abort (a panic here).

CI runs five build variants in `.github/workflows/build.yml` (standard / debug / no-batt-led / 320 MHz fallback / Pico W), with ARM's official toolchain from `tools/toolchain.env` (15.2.Rel1, cached tarball, as upstream 425061f / 994f310), not Ubuntu's `gcc-arm-none-eabi`. A build folder can't switch SDK or compiler (CMake caches both): use a fresh one, as `tools/dev_firmware.sh` does by itself. When changing build flags or CMake, update the workflow accordingly. CI, `release.yml` and `tools/release.sh` also run the host tests, `tools/check_gitlinks.sh` and `tools/check_ram_residency.sh ELF` (core1's audio path and, on RP2350, core0's BT/USB hot path in RAM, no `__mem*_chk`) and `tools/check_xip_setup.sh ELF [clkdiv [vcode]]` (non-empty `.boot2`; on RP2350 the embedded XIP setup is called by crt0, its flash divider, and `main()` starting with `vreg_set_voltage(code)`); add a symbol there when core1 gets a new per-frame function or core0's hot path a new RAM function.

**`lib/opus` and `lib/WDL` are submodule gitlinks (mode 160000): never replace them with a symlink, never stage anything under `lib/`, no `git commit -a` over them.** `tools/check_gitlinks.sh` fails the build otherwise (5d869f1 committed a symlink once).

## Hardware-in-the-loop workflow

Host unit tests (`tests/host/run.sh`) cover the pure logic only; everything else is verified on hardware. To verify a change:

1. Build → produces `build/ds5-bridge-oled.uf2`.
2. Put Pico into bootloader: hold BOOTSEL, plug USB. It mounts as `/run/media/$USER/RP2350` (Linux) or `RPI-RP2` (others).
3. Copy the UF2 to the mount: `cp build/ds5-bridge-oled.uf2 /run/media/$USER/RP2350/` — Pico auto-reboots into the new firmware.
4. Pair a DualSense: hold Create + PS on the controller until the lightbar pulses; the dongle inquiry picks it up.
5. Verify enumeration host-side: `lsusb | grep 054c:0ce6` should show `Sony Corp. DualSense wireless controller (PS5)`.

The development cadence is **one feature per UF2 + checkpoint with the user before moving on** — the user has hardware in front of them, regressions are caught the same minute, and large multi-feature commits make root-causing hard.

## Architecture

**Two cores, asymmetric workload:**

- **Core 0** runs everything: `main()` infinite loop in `src/main.cpp` drives `cyw43_arch_poll()` → BTstack, `tud_task()` → TinyUSB, `audio_loop()` (USB → BT haptic path), `interrupt_loop()` (BT → USB HID path), and `oled_loop()`.
- **Core 1** runs only `core1_entry()` in `src/audio.cpp`: the Opus speaker encoder and the mic Opus decoder + packet-loss concealment. It runs **from RAM** (see gotcha below). The cores talk only through Pico SDK `queue_t`s: `audio_fifo` (raw speaker PCM → core1), `audio_spk_fifo` (encoded speaker → core0), `mic_fifo` / `mic_decode_fifo` (mic Opus → core1 → decoded PCM → core0). Core0 also owns `haptics_fifo`.

**Two parallel data paths through the firmware:**

1. **HID** (DS5 input → host, host output → DS5): `src/bt.cpp` registers `on_bt_data()` → `src/main.cpp:on_bt_data()` → updates `interrupt_in_data[63]` → `tud_hid_report()`. Output reports come the other way through `tud_hid_set_report_cb`.
2. **Audio** (host USB audio → DS5 speaker + haptics): `src/audio.cpp:audio_loop()` reads 4-channel USB UAC1, splits ch1/2 (speaker → Opus encode on core1) and ch3/4 (haptic → 48k→3k by taking every 16th frame, `src/haptics_decimate.h`, upstream 4929996; byte-identical to the WDL resampler it replaced, which now serves only the speaker), and `audio_bt_task()` sends one **`0x39`** report once two haptic + two speaker frames are queued (upstream's packed format). Controller **state** (triggers, LED, rumble) is *not* in audio frames: every host `0x02` output report is forwarded immediately as a `0x31` (`tud_hid_set_report_cb`), and volume (`state_set_volume`, driven by the host UAC1 volume) and mic-stream on/off (`update_mic_status`, a `0x32`) go out as one-off reports. Mic: DS5 mic Opus arrives in mic-tagged `0x31` input reports → core1 decode → `mic_drain()` feeds USB IN in 1 ms slices, only while the host has the mic interface open.

**BT layer:** Uses Pico SDK's bundled BTstack (no separate clone). `src/bt.cpp` is the only file that touches HCI/L2CAP. Inquiry (the active scan for a controller in pairing mode) runs only in a pairing window (`src/scan_policy.h`): boot, a slot switch / forget / wipe, a failed authentication, KEY0 held 2 s on the OLED Status screen with no controller (`bt_pair_now`, the board-side "pair now": with no controller the board is off USB, so the app can't); never restarted forever. The Status screen counts a pairing window down (`bt_pairing_seconds_left`, `src/pair_prompt.h`). Paired controllers reconnect by paging the dongle (page scan is always on), so they never need it. PSMs are `PSM_HID_CONTROL` and `PSM_HID_INTERRUPT`. Link keys live in BTstack's TLV NVM with `NVM_NUM_LINK_KEYS=4` (configured in `src/btstack_config.h`).

**OLED add-on is optional and self-contained:** All 10 screens, the SH1107 SPI driver, the 5×7 font, the icon table, and the input handling live in `src/oled.cpp` (~30 KB). The only outward dependencies are read-only accessors (`bt_is_connected`, `bt_get_addr`, `audio_peak_*`, `bt_get_signal_strength`, the new slot accessors) and the global `interrupt_in_data[63]` (read-only for input visualization). When no OLED is wired, the SPI writes go nowhere — no init check needed.

**Idle power ladder (`oled_loop` tail):** Three-stage state machine (`OLED_ACTIVE` → `OLED_DIM` → `OLED_OFF`) driven by `last_activity_us`. `kAutoDimUs = 2 min` enters Dim — the regular per-screen render is replaced with `render_dim_pulse()`, which clears the framebuffer and walks a 2×2 dot through 8 positions every 30 s, blinking 1 s on / 1 s off. `kAutoOffUs = 15 min` enters Off — `cmd(0xAE)` puts the SH1107 to sleep and `oled_loop` returns early before rendering. Wakes on KEY0/KEY1 (via `handle_buttons` bumping `last_activity_us`), `bt_is_connected()` rising edge, or any change in the `interrupt_in_data[0..9]` hash. The dim tier uses `flush_fb_raw()` (the chrome-less variant) since there's no nav target while asleep. **Why this shape:** the SH1107 contrast register has a heavily non-linear perceptual curve on the Waveshare panel — even `0x02` looks ~90 % as bright as `0xFF`. The only reliable "dim" available is rendering fewer pixels.

**Multi-slot pairing (Phase G):** Storage is two-tier:

- **Link keys** stay in BTstack's TLV NVM (4 slots, unchanged from upstream).
- **bd_addrs + occupancy** in a custom flash sector owned by `src/slots.cpp` — sector below the config sector (`PICO_FLASH_SIZE_BYTES - 2*FLASH_SECTOR_SIZE`).

Slot routing is enforced in `src/bt.cpp`'s `HCI_EVENT_INQUIRY_RESULT` handler: skip devices owned by other slots, accept only the current slot's bd_addr if occupied, auto-assign on first `L2CAP_EVENT_CHANNEL_OPENED` for HID_CONTROL when the current slot is empty. Switching slots flows: `bt_set_slot()` → persist new index → `bt_disconnect()` → `HCI_EVENT_DISCONNECTION_COMPLETE` → restart inquiry under new filter.

**Flash layout** (top of flash, growing downward):

| Sector | Owner | Contents |
|---|---|---|
| `PICO_FLASH_SIZE_BYTES - 1*FLASH_SECTOR_SIZE` | `src/config.cpp` | `Config{magic, version, crc32, size, body, power_flags}` — the 50-byte `Config_body` incl. `current_slot` (grow it only by appending; see protocol 1.13 for the 0xF7 GET limit), then `power_flags` (protocol 1.14, outside the CRC) |
| `PICO_FLASH_SIZE_BYTES - 2*FLASH_SECTOR_SIZE` | `src/slots.cpp` | `SlotsData{magic, addrs[4][6], occupied[4]}` |

(Those two rows are the historical offsets; the real ones are in `src/flash_layout.h`, see below.) The calibration sector (`CALIB_FLASH_OFFSET`, bank −4, `src/calib.cpp`) holds `CalibData{magic, ver, body[4], curve[4][2]}`: the stick response curves (proto 1.10) were appended **after** the four calibration bodies (a `static_assert` pins their offset) instead of taking a new sector, so older firmware still reads the calibration (same magic/ver/bodies) and calibration saved by older firmware reads its curves as Linear (the rest of the page is 0xFF, and any invalid curve loads as Linear on its own without resetting the calibration). Grow `CalibData` only by appending, and keep it within one page (`static_assert(sizeof(CalibData) <= FLASH_PAGE_SIZE)`, 149 bytes now).

`config_save()`, `save_slots_to_flash()` and the remap save all go through `flash_sector_write()` (`src/flash_safe.h`), which uses `flash_safe_execute()` to park core1 in RAM during erase/program (`PICO_FLASH_ASSUME_CORE1_SAFE=0`; core1 calls `flash_safe_execute_core_init()`). Boot-time writes before core1 starts fall back to plain IRQ masking.

**Sectors live in `src/flash_layout.h`, directly below BTstack's TLV bank** (`PICO_FLASH_BANK_STORAGE_OFFSET`, which on RP2350 is the 2 sectors below the last): config at bank −1, slots −2, remap −3. They used to be at −1/−2/−3 of flash, overlapping the bank — never put anything inside `[PICO_FLASH_BANK_STORAGE_OFFSET, +PICO_FLASH_BANK_TOTAL_SIZE)`. `config_load()` migrates a valid config from the old last-sector location once. `flash_safe_execute` is wrapped at link time (`__wrap_flash_safe_execute` in `src/main.cpp`): before core1 registers for lockout it runs the write with core0 IRQs masked (the SDK would refuse with `NOT_PERMITTED` and BTstack's write would be lost), and it counts calls/failures for `0xF5`.

## Critical gotchas

These are non-obvious from the code; they cost time when forgotten.

- **The Pico 2 W runs at stock 150 MHz, like upstream; the old 320 MHz @ 1.20 V was not load-bearing.** The overclock was inherited from upstream awalol, and our note that "stock clock or 1.10 V breaks the CYW43 PIO SPI bus" came from tests that kept the CYW43 PIO divider at 5, which only suits 320 MHz. Upstream v0.7.0 runs 150 MHz with PIO divider 2 (a023371), and so do we: tested on issue #15's board (pairs, buttons, haptics, 0 drops, core1 speaker frame 5.0 ms avg / 6.5 ms max). 1.20 V is also above the RP2350's 1.16 V operating maximum. Three things belong together, so don't change one alone: (1) `main()` sets `VREG_VOLTAGE_DEFAULT` (1.10 V) at 150 MHz instead of skipping the regulator, because the RP2350 keeps its VREG setting across every reset but power-on (a dongle flashed from 320 MHz firmware stayed at 1.20 V); (2) `PICO_EMBED_XIP_SETUP=1` with `bs2_default`'s `PICO_FLASH_SPI_CLKDIV` (upstream's rule: 4 above 266 MHz, else 2), so crt0 sets the flash up at boot instead of leaving the bootrom's setting, which made core1 crash on some boards (issue #15); (3) the CYW43 PIO divider follows the clock. CMakeLists.txt fails an RP2350 configure without the embedded XIP setup or with the flash above 100 MHz, and `tools/check_xip_setup.sh` checks the ELF. `DS5_CLOCK_KHZ=320000` still builds the old setup for one release. The Pico W (RP2040) is unchanged: 200 MHz, divider 3, and its boot2 always runs.
- **Render functions are `__attribute__((noinline))` on purpose.** With aggressive inlining the compiler folds all 10 `render_screen_*` into `oled_loop()`, which then exceeds Thumb's 4 KB literal-pool reach and the linker emits `dangerous relocation: unsupported relocation`. If you remove the noinline attributes or merge two render functions into a single huge one, the build will fail at link time. The symbol size grows over time as screens get richer — the lambda inside `render_screen_settings` was already hoisted to a noinline `format_settings_item()` for the same reason.
- **`config_default()` is implemented in this fork**, not upstream. Upstream declares it in `config.h:30` but never defines it. The implementation in `src/config.cpp` fills the body with `0xFF` and re-runs `config_valid()` (matches a freshly-erased flash sector). Don't assume any header declaration is implemented just because it compiles — check the .cpp.
- **Screen indices are symbolic.** `kScreenStatus`, `kScreenSlots`, `kScreenLightbar`, … are defined in a single block near the top of `src/oled.cpp`. `oled_loop()`'s switch and `handle_buttons()`' KEY1 contextual checks (Trigger preset cycle, Lightbar mode cycle) refer to them by name. Never hard-code integers — reorder = one-block edit.
- **OLED `kPin*` pinout is hardcoded** to the Waveshare Pico-OLED-1.3 standard (`kPinMOSI=11`, `kPinCLK=10`, `kPinCS=9`, `kPinDC=8`, `kPinRST=12`, `kPinKey0=15`, `kPinKey1=17`). SPI1 instance. Conflicts with anything else on those pins. Pico's BT chip uses internal SPI to CYW43 (different bus), and USB / UART pins (GP0/GP1) are also free — no conflicts in default config.
- **DS5 PS+Mute hold-2-seconds → `watchdog_reboot(0,0,0)`** is the headless soft-reboot path (see `src/main.cpp:interrupt_loop()`). It checks `interrupt_in_data[9]` bits 0+2. If you change input report layout, this combo breaks silently.
- **Inactivity-disconnect uses `packet[3..12]`** in the L2CAP interrupt data path (`src/bt.cpp:l2cap_packet_handler`). It's looking at sticks and DPad/buttons to decide "idle." Don't touch those bytes' layout without updating the heuristic.
- **Core1's audio path must stay in RAM.** Running libopus / the resampler from flash made core1 miss its encode deadline (core0's BTstack/TinyUSB/OLED evict the shared XIP cache) and drop ~7 % of speaker chunks — the long-standing speaker crackle. CMakeLists.txt renames libopus `.text`/`.rodata` and the two `WDL_Resampler` hot methods into `.time_critical.*`, `relocate_to_ram()` moves SDK queue ops, `src/ram_mem.c` overrides `memcpy`/`memset`/`memmove`, and core1 functions are `__not_in_flash_func`. Anything new core1 calls per frame must be RAM-resident too. The OLED Diagnostics `Drop r/e/h` row is the tripwire: `r` climbing = core1 too slow.
- **Core0's Bluetooth/USB hot path is in RAM too (RP2350 only)**: upstream's B.1–B.4, a2772a9, 57f185b and `audio_loop` (~39 KB of SRAM). Our functions use `CORE0_RAM_FUNC` / `CORE0_RAM_DATA` (`src/core0_ram.h`; plain flash on the Pico W, whose RP2040 can't spare the RAM); SDK functions are renamed by `relocate_to_ram()` in CMakeLists.txt under `if (PICO_RP2350)`. Section names must match the SDK's TinyUSB (0.21 now: the FIFO bulk movers are `tu_fifo_{read,write}_n_access_mode`; `tu_fifo_read_n`/`write_n`/`count` are inline wrappers without a section, upstream 76690ab): a rename that matches nothing does nothing, so every one is listed in `tools/check_ram_residency.sh` (`file.c:sym` for a static symbol) — add new ones there, and recheck the list when the SDK/TinyUSB moves.
- **Core1 must stay registered for flash lockout** (`flash_safe_execute_core_init()` in `core1_entry`, `PICO_FLASH_ASSUME_CORE1_SAFE=0`). Its RAM code still calls flash every frame (soft-double helpers, libm, the resampler's malloc), so an unparked flash write kills core1 — `0xF5` shows `c1_loops` frozen and every chunk dropped.
- **Per-stage timings (protocol 1.11, `src/perf.h`)**: core0's main loop is timed per stage (whole pass, `cyw43_arch_poll`, `tud_task`, audio, input, `oled_loop`) and core1 per speaker frame and per mic frame: average and max, in `0xFC` [11..62], reset with `0xF6 0x15`. Cycle counter (DWT) on RP2350, microsecond timer on RP2040. Use them to A/B a build change on hardware (`-O2` vs `-O3`, an Opus option): flash build A, reset, run the same load (e.g. a game with speaker audio) for a minute, read `0xFC`; repeat with B. `perf_record` is inline so core1's RAM code can call it; keep anything core1 adds that way.
- **A failed save outside Settings / Slots goes to `oled_notice()`** (`src/oled_toast.h`): a 3 s inverted status line over the bottom row of whatever screen is up, drawn in `flush_fb()`; when it ends `fb_generation` is bumped so Diagnostics (which redraws only changed rows) redraws in full. Use it for any new OLED-side failure without its own footer.
- **Feature reports: `bt_request_feature()` when you only want the GET sent, `bt_feature_copy()` (a stack buffer) for anything polled per pass**; `get_feature_data()` / `bt_peek_feature()` return a `std::vector` copy and are for rare callers only (lifetime pass batch 3: no heap on core0's loop).
- **The OLED flush skips unchanged frames** (`flush_fb_raw`: `memcmp` against `fb_shown`, still resent every 20th frame so a disturbed panel heals) and sends a frame in 129 SPI transactions (`src/oled_flush.h`, byte-identical to the old per-byte flush, checked by the host tests); the mirror's frame counter still counts every frame.
- **Use the `0xF5` counters first** (`scripts/audio_diag.py [secs]`): they show USB-in, BT-out, drops, core1 liveness and flash write failures from the host, no OLED reading needed. Layout (63 bytes, the cap of both transports): 15 u32 counters at [0..59], then core1 health: [60] flags (bit0 started, bit1 speaker encoder failed, bit2 mic decoder failed, bits 3..6 core1's start-up stage, bit7 = this layout) and [61..62] u16 free heap at core1 start in KiB (0 = not known). Firmware 0.9.4–0.9.5-dev.5 sent the health as two more u32s (68 bytes), so hosts only ever got the flags' low byte at [60] and zeros after it; bit7 tells them apart, no protocol bump. The stage (`g_c1_stage` in `src/audio.cpp`, issue #15) is the last start-up step `core1_entry` reached: 0 never entered, 1 entered, 2 flash lockout registered, 3 cycle counter on (free heap read next), 4 creating the speaker encoder, 5 encoder created or failed, 6 encoder + resampler set up, 7 creating the mic decoder, 8 decoder created or failed, 9 in the loop (set at the top of every pass; running = 9 and `c1_loops` moving). A core1 that never loops shows the step it stopped in; the Pico W build (no speaker) goes 3 → 7. Every firmware with bit7 sends it. Every reply must fit in 63 bytes (`cmd_no_reply_needs_more_than_63_bytes` host test).
  More host-side tools: `scripts/session_monitor.py LOG` logs all counters every 2 s and tags each line with the running game (auto-detected); `scripts/out02_dump.py` decodes the last host output report and the last one carrying trigger effects (`0xF3`/`0xF4`), e.g. to see whether a game is sending zero-force triggers; `scripts/get_ring.py` lists the last 16 feature-report GETs and how many bytes the dongle answered (`0xF2`).
- **The `0x39` audio report is 547 bytes** (+1 header byte): `send_element` in `src/bt.cpp` is sized to the interrupt MTU (672). Shrinking it overflows silently (silent speaker, hung USB audio). The DS5 amp needs `AllowSpeakerVolume` + a volume: clearing those bits makes the speaker go silent.

- **The DualSense HID descriptor must stay byte-identical to a real DS5 (289 bytes), and `0x09`/`0x20`/`0x05` feature reports must return the controller's *real* cached data — or native game triggers silently break.** A game's native DualSense detection (Cyberpunk, etc.) validates *both* the descriptor shape and the feature-report *content*, then drives adaptive triggers over the native hidraw path. If either differs from genuine hardware the game falls back to a generic/Xbox pad and triggers never fire. Linux's `hid_playstation` is far more lenient (size + CRC only), so the dongle still *binds* and the on-dongle OLED trigger-test still works — which masked this break for weeks. Two load-bearing things: (1) **don't re-declare config reports `0xF6`–`0xF9`** in `desc_hid_report_ds` (or bump its `wDescriptorLength` runtime patch in `tud_descriptor_configuration_cb` back to `0x41`) — that's what made the descriptor 321 bytes and killed triggers; (2) keep `tud_hid_get_report_cb` serving the **real `init_feature()` cache** for `0x09`/`0x20`/`0x05`, with the CRC-valid synthetic stub only as the pre-BT-link probe fallback. One deliberate exception (`src/fw_report.h`, upstream ae83907): an Edge presented as a DualSense (controller mode DS5) gets a pinned DualSense `0x20` so PS Accessories doesn't offer a failing update; a DualSense in any mode and an Edge in Auto/DSE mode get their real `0x20`, and the cache itself (the app's Controller info) always holds the real one. Edge detection reads that cached `0x20` ([22] = 0x44), the last of `init_feature()`'s requests, and connects USB on its reply. `desc_hid_report_dse` (DSE mode) still declares F6-F9 and needs the same cut. Host side requires a Proton with the Wine `winebus.sys` #9034 fix + `PROTON_ENABLE_HIDRAW=0x054c/0x0ce6` + Steam Input off; diff a dongle vs real-DS5 `PROTON_LOG=+hid` capture to debug (a GET retry storm on `0x20`/`0x09` = the dongle's feature content is being rejected).

## Versioning — single source of truth

The release tag is the **only** place the version is written. Everything else flows from it:

- **Release tag** (e.g. `v0.6.2-oled-edition`) → created with `git tag` then `gh release create`.
- **`.github/workflows/release.yml`** picks the tag up as `$FIRMWARE_VERSION` and passes it to CMake via `-DVERSION="$FIRMWARE_VERSION"`.
- **`CMakeLists.txt`** exposes it to C++ as a compile-time macro:
  ```cmake
  target_compile_definitions(ds5-bridge PRIVATE FIRMWARE_VERSION="${VERSION}")
  ```
  Local builds without `-DVERSION=...` get the default `"dev"` — that's a deliberate visual signal so an untagged build is obvious on the OLED Status header.
- **`src/oled.cpp` `render_screen()`** renders `"DS5 B. "` + the version without `-oled-edition` (`src/version_label.h`, compile time; `+N.hash` build metadata kept) for the Status screen header: 19 characters fit between the chrome strip and the link icon, a longer one scrolls ping-pong (`draw_title_scrolling`, clipped before the icon). The boot splash shows the same short version. No string literal for the version exists anywhere else in the firmware source.
- **Web preview** (`DS5Dongle-OLED-Config-Web`) reads the same tag at runtime from `public/firmware-latest.json`, which CI bundles in `.github/workflows/deploy.yml`'s "Bundle latest firmware UF2 from GitHub releases" step (it pulls from `MarcelineVPQ/DS5Dongle-OLED-Edition/releases/latest` via the GitHub API). `OledEmulator.tsx` fetches that JSON on mount and writes the short form (suffix `-oled-edition` stripped) into `state.firmwareVersionLabel`, which `screens.ts:renderStatus` consumes.

**Releases** ship the firmware *and* the configurator app as one release with one version (user decision 2026-10-10; app ADR-0005):

1. CHANGELOGs: move `[Unreleased]` into `## [X.Y.Z-oled-edition]` here and `## [X.Y.Z]` in the app repo; commit both on `master`. After development builds, that section is a summary on top and the `[X.Y.Z-dev.N]` sections stay below it.
2. `tools/release.sh X.Y.Z` (expects the app repo at `../DS5Dongle-OLED-Config-Web`, or `--app PATH`). It runs the app's checks and a release-configuration firmware build, sets the app version, then asks before pushing: commits the version bump in the app repo (for a development build also the new CHANGELOG sections, in both repos) and pushes the tag `vX.Y.Z-oled-edition` to **both** repos. Only run it when the user says "release".
3. The tag starts `.github/workflows/release.yml`: firmware (with `-DENABLE_COMPANION_VENDOR=ON`), the app on Linux/Windows/macOS with that UF2 bundled in `resources/firmware/`, then one release with everything attached and `SHA256SUMS.txt`, published as a draft first and made public only when complete. Then `manifest.yml` rebuilds `latest.json` (the app's update feed) on `master`. **The feed is signed:** `manifest.yml` signs `latest.json` with the Ed25519 key in the `MANIFEST_SIGNING_KEY` Actions secret (`tools/sign_manifest.mjs` → `latest.json.sig`) and fails without it; the app refuses an unsigned or tampered feed (its `electron/main/feedSignature.ts` lists the trusted public keys). The private key's only other copy is on the developer's PC (`~/.config/ds5-release/manifest-signing-key.pem`). To rotate: add the new public key to the app's `TRUSTED_KEYS`, release, then switch the secret. The publish job also attests build provenance for every file (`gh attestation verify FILE -R MarcelineVPQ/DS5Dongle-OLED-Edition`).

**Dev firmware builds:** `tools/dev_firmware.sh [--flash] [--picow]` stamps the version from Git (`v0.9.3-oled-edition+3.a1b2c3d[.dirty]`: the OLED header, the app's firmware version and picotool all show it), builds in `~/.cache/ds5dongle/build-<board>/`, and with `--flash` sends BOOTSEL (`tools/bootsel.py`, over HID) and copies the UF2. A plain cmake configure without `-DVERSION` gets the same Git stamp (CMakeLists.txt), never a stale cached value; releases pass `-DVERSION=vX.Y.Z-oled-edition`.

**Development builds** (the app's opt-in Development channel): `tools/release.sh X.Y.Z-dev.N` tags `vX.Y.Z-dev.N-oled-edition`; the same workflow builds it, publishes it as a **GitHub pre-release** (notes from the build's own CHANGELOG sections: release.sh renames `[Unreleased]` to `## [X.Y.Z-dev.N-oled-edition] - date` here and `## [X.Y.Z-dev.N] - date` in the app, adds a fresh empty `[Unreleased]` and commits both with the release; it refuses when both `[Unreleased]` are empty), and `manifest.yml` writes `latest-dev.json` (+ `.sig`): the newest of the development pre-releases and the stable releases (`tools/manifest_lib.mjs selectRelease(releases, "dev")`). `latest.json` never lists a pre-release. Use it to try risky firmware (e.g. upstream's clock changes) on your own dongle first.

**READMEs in 7 languages:** `README.md` is the reference; `README.CN.md`, `README.DE.md`, `README.ES.md`, `README.FR.md`, `README.JA.md` and `README.PT-BR.md` mirror it, one per language the app ships, with one identical language bar on line 3. Every README.md change (including the Development-channel note's version at each development build) goes to all 7 in the same commit, with the app's glossary (`../DS5Dongle-OLED-Config-Web/docs/GLOSSARY.md`) and locale labels for each language. `python3 tools/check_readmes.py` fails on a missing file, a differing language bar, heading structure or dev version, or a broken link or anchor; it runs in `build.yml`, `release.yml` and `tools/release.sh`.

Other releases here (`proton-*`) are never touched by the workflow: it only runs on `v*-oled-edition` tag pushes.

There is **no other place** to edit the version. If you find a hardcoded version string in source (`"v0.6.0"`, `"v0.5.4"`, etc.), it's a bug — replace it with the macro / JSON lookup.

## Loop pass

A standing rule, shared with the app (its CLAUDE.md "Loop pass" has the full text). Never sample hot paths by eye.

1. **Every loop in `src/` carries a verdict comment**, added in the same commit as the loop: `// loop: VERDICT — reason`, on the loop's line or the line above. `python3 tools/list_loops.py --check` fails without one; it runs in `build.yml` and `release.yml`.
2. **`tools/list_loops.py` lists every `for`/`while`/`do` loop** (standard library only, a brace-aware scanner; `lib/` is excluded). For each loop it gives the function, where it runs (core1, core0's main loop, a TinyUSB/BTstack/flash callback, an ISR, boot; worked out from a call graph over `src/`), whether it spins or polls a timeout, its nesting, and whether it touches flash.
3. **Verdicts:**
   - **HOT-PATH-OK**: runs per pass, frame or callback, but N is small and bounded. State N.
   - **FIX-HOT-PATH**: unbounded or blocking work on core1, flash access on core1, a busy-wait without a timeout, or heavy per-pass work on core0's loop.
   - **BATCH**: one SPI/USB/BT transaction instead of N.
   - **SERIAL-REQUIRED**: give the reason (protocol order, a data dependency, a deadline).
   - **NOT-WORTH**: boot-only, rare, compile-time or host-test-only, or tiny N.
   - **PARALLELIZE**: rare here (one core per job).
4. **Re-run the full pass when a release touches a hot path** (core0's loop, core1, the BT/USB callbacks). Run the lister, re-check every verdict, and update the firmware tables in the one doc, which lives in the app repo: `../DS5Dongle-OLED-Config-Web/docs/LOOP_PASS_2026-10.md` (or its newer `LOOP_PASS_<date>.md`). Don't keep a copy here.

## Error pass

A standing rule, shared with the app (its CLAUDE.md "Error pass" has the full text): **no silent failure.** Every error a user action can hit (an 0xF6 SET from the app, an OLED button) reaches the user: a result code in 0xF1 (`CMD_RESULT_INVALID` / `FAILED` / `BUSY`, which the app turns into a message), an OLED message (`"Save FAIL"`, `"Wipe FAIL"`), or a flag/counter the app shows. Anything else is deliberately logged or counted, with a one-line reason the user needn't see it.

1. **Every failure path in `src/` carries a verdict comment**, added in the same commit as the code: `// error: VERDICT — <surfaces as>; <why>` (optionally ` Change: <fix>`), on the line or in the comment block above. `python3 tools/list_errors.py --check` fails without one; it runs in `build.yml` and `release.yml`.
2. **`tools/list_errors.py` lists them mechanically** (standard library; it reuses `list_loops.py`'s scanner and call graph): a fallible call whose result is dropped or checked (BTstack / TinyUSB / flash / queue / Opus / cyw43 status, and `src/`'s own `bool` / `Ok|Invalid|NotSaved` functions), `return false` / `-1` / `nullptr` / an Invalid or NotSaved value, `CMD_RESULT_INVALID|FAILED|BUSY`, a magic/CRC check on stored data, a drop/error counter, and `if (...) return;` in a void user-action handler.
3. **Verdicts:** SHOWN (cite the result code / OLED string / flag), LOGGED-OK (printf/counter + why the user needn't see it), SILENT-BUG (a user action fails with nothing shown: fix it), SWALLOWED (discarded without a reason: fix or justify), NOT-WORTH (can't fail in practice; say why).
4. A function that saves to flash returns whether the save worked (`bool` or `...::NotSaved`) and its callers report it: never drop a save's result.
5. The full table lives once, in the app repo: [`docs/ERROR_PASS_2026-10.md`](https://github.com/MarcelineVPQ/DS5Dongle-OLED-Config-Web/blob/master/docs/ERROR_PASS_2026-10.md). Don't keep a copy here.

## Lifetime pass

A standing rule, shared with the app (its CLAUDE.md "Lifetime pass" has the full text). Never review allocations by eye.

1. **Every acquisition in `src/` names its release point, in the same commit that adds it**: `// lifetime: VERDICT — release point or reason`, on its line or in the comment block right above. `python3 tools/list_lifetimes.py --check` fails without one; it runs in `build.yml` and `release.yml`.
2. **`tools/list_lifetimes.py` lists every acquisition** (standard library only; it reuses `tools/list_loops.py`'s scanner and call graph, so "Runs on" means the same): heap allocations (`malloc`/`calloc`/`realloc`/`new`/`make_unique`, `queue_init`, `opus_*_create`, the resampler's `Prealloc`), every `std::` container object, every function returning one by value and every call that gets a copy from one, container growth (`push_back`, `assign`, `map[key] =`), timers/alarms (`add_alarm_*`, `add_repeating_timer_*`, BTstack timers) and handler registrations (BTstack, IRQs, core1 launch).
3. **Verdicts:** **OK** (name where it is freed: a disconnect clears it, reused in place, once per connection), **LEAK** (never freed / grows without bound: state the impact), **WASTE** (work or memory kept after it's no longer needed), **HOT-ALLOC** (heap use per main-loop pass, per report or on core1's frame path: core0's loop and core1 should not touch the heap), **NOT-WORTH** (boot-only and lives until reset by design, or rare and small: say why).
4. **Re-run the full pass when a release adds allocations, containers or callbacks.** Run the lister, re-check every verdict, and update the firmware tables in the one doc, which lives in the app repo: `../DS5Dongle-OLED-Config-Web/docs/LIFETIME_PASS_2026-10.md` (or its newer `LIFETIME_PASS_<date>.md`). Don't keep a copy here.

## Where features live

When asked to modify behavior, the *first* file to read is usually one of:

- New BT pairing / connection state behavior → `src/bt.cpp` (HCI + L2CAP event handlers).
- New OLED screen or change to existing one → `src/oled.cpp`.
- New diagnostic counter on the OLED Diagnostics screen → bump `kNumDiagRows` in `src/oled.cpp` and add a `case` to `format_diag_row()` (single switch, one row per case). The screen scrolls automatically; no D-pad wiring needed. Counters that need rate-per-second arithmetic should be sampled in `sample_diag_rates()` and read from `g_diag_rates`. Counter globals themselves typically live in `src/main.cpp` next to `g_bt_31_packets` etc. with `extern` declarations near the top of `src/oled.cpp`.
- Host-side diagnostics → `scripts/mic_diag.sh` (Linux only, reads `/dev/hidraw` directly). Subcommands: `status` / `capture [secs]` / `watch` / `bt-trace`. `bt-trace` reads the firmware's `0xFD` vendor feature report (defined in `src/cmd.cpp`'s `tud_hid_get_report_cb`), which currently exposes BT-input counters + the host-output trigger-flow counters. To add a new counter visible to `bt-trace`: extend the `0xFD` payload in `src/cmd.cpp` (bump `want`, write at the new offset), bump `IOCTL_SIZE` in `bt_trace()` of the script, and add the field to its `decode()` dict. The `0xFD` report ID is not declared in the HID descriptor (Linux hidraw ioctls don't enforce that; WebHID would reject undeclared IDs, which is why config goes through `0xF6`).
- New persistent config field → `src/config.h` (struct, appended; update the `sizeof` `static_assert`), `src/config.cpp:config_valid()` (defaults + clamping; erased flash is 0xFF, so 0xFF must be invalid), `src/oled.cpp:format_settings_item()` (UI), `src/oled.cpp:settings_adjust()` (D-pad ▶◀ behavior), a protocol minor + feature bit, and the app's `src/protocol/config.ts`. The whole body must stay shorter than 63 bytes (the 0xF7 rule under protocol 1.13). Update `CHANGELOG.md`.
- USB descriptor or interface change → `src/usb_descriptors.cpp` + `src/tusb_config.h`.
- DualSense Edge profiles for PS Accessories → `src/dse.{h,cpp}` (upstream 8a2f576, every build). On the Edge's 0x20 reply `bt.cpp` calls `dse_on_connect()`; `dse_task()` (in `cmd_task`) then sends SET 0x65 = cached 0x20 bytes 1..61 raw (`bt_send_control`, no crc; our cache keeps the id at [0], upstream's doesn't since 2efc855) and SET 0x80 [0x70, 0x01] (59 bytes, crc by `set_feature_data`), waits 4 s, and GETs 0x70–0x7B one per 80 ms (a burst drops requests). Until 80 ms after the last GET, `get_report_impl` refuses (stalls) host GETs of 0x70–0x7B (still forwarding the GET, as upstream), so PS Accessories retries; USB connects at once. `get_feature_data` always refreshes 0x70–0x7B in the background. A forwarded host SET 0x60–0x62 on an Edge (`dse_on_profile_write`) → 0.5 s later SET 0x80 [0x70, 0x01], 6 GET 0x81 250 ms apart from 0.5 s after it, refetch 5 s after it (reads stay open; a new write restarts it; a write during the connect sequence runs after it). **One controller test slot (0x80/0x81), three users, arbitrated in `cmd_task`:** while `dse_owns_test_slot()` (connect until its fetch ends, write until its refetch ends) the colorway read doesn't start and an app test stays queued; `dse_task` sends its 0x80 only while the colorway read isn't polling and `ctrl_test_holds_slot()` is false (sent or in its 1 s scrub; a queued test doesn't hold it, so no deadlock). Host SET 0x80 / GET 0x81 are still forwarded during the DSE sequence (the app runs its own unlock; only the dongle's own test blocks them). Disconnect → `dse_reset()`. The 0x09/0x20/0x05 paths and the 289-byte descriptor are untouched.
- PC sleep / wake, and what the dongle presents on USB (nothing, the DualSense, or the wake-only keyboard) → `src/usb_power.h` (pure state machine, host-tested) + `src/usb_power.cpp` (TinyUSB callbacks, `usb_power_task()` in the main loop). Apart from the boot detach in `main()`, nothing else calls `tud_connect` / `tud_disconnect`: bt.cpp reports the controller with `usb_power_controller()`, 0xF6 0x03 is `usb_power_reconnect()`. Rules it keeps: the bus is never touched while suspended (a hot-plug wakes a sleeping PC), remote wakeup only through `tud_remote_wakeup()` (never `dcd_remote_wakeup()`, which skips the host's permission), no BOS / MS OS 2.0, and the full configuration with "PS wakes the PC" off is byte-identical to before. The wake keyboard has its own VID/PID (2E8A:000A) so nothing binds it as a DualSense; while it is up (`usb_wake_keyboard()`) HID instance 0 is the keyboard, so nothing may send DualSense reports.
- Desktop configurator transport → `src/vendor_itf.{h,cpp}` (CMake `ENABLE_COMPANION_VENDOR`, default OFF). A control-only, class-0xFF interface appended after every other interface, so `CONFIG_DESC_LEN_BASE` stays the patch anchor and the 289-byte DS descriptor is untouched. It carries the same `0xF5`–`0xFE` pico commands as the HID feature reports, plus the `0xF2`–`0xF4` debug reports (on the HID path only in `ENABLE_SERIAL` builds: a real DS5 has feature reports `0xF2`/`0xF4`, so release builds pass them through to the controller): GET = `0xC1`/bRequest `0x01`/wValue=id (payload has no report-id byte), SET = `0x41`/bRequest `0x02`, max 63 bytes, SET runs after the status stage. Windows binds WinUSB through **MS OS 1.0** descriptors (string `0xEE`, compat ID, `DeviceInterfaceGUIDs` = `{CD1F1B79-799E-44AC-ADFC-A3F2090D1D4A}`); not 2.0, which needs bcdUSB ≥ 0x0201 + BOS and would change the device descriptor. Every VENDOR-type request goes to `tud_vendor_control_xfer_cb` before TinyUSB's recipient dispatch, so the class driver (`usbd_app_driver_get_cb`) only claims the interface. Linux probe: `~/projects/ds5-companion-probe/vendor_probe.mjs` / `vendor_cmd.mjs` (npm `usb`).
- Configurator protocol → `src/cmd.cpp`. `0xF1` identity (vendor interface only; a real DS5 uses `0xF1` for firmware update, so the HID path never routes it): magic `DS5O`, protocol major.minor (`PICO_PROTO_*` in `cmd.h`), config body length, feature bits, u16 SET sequence, last function + result (`CMD_RESULT_*`), u32 host config generation, slot count/current slot/BT connected; protocol 1.1 adds (when wLength ≥ 25) controller flags (bit0 charging, bit1 full), the current lightbar RGB and battery level in 10 % steps. Protocol 1.2 adds identity [19] bit 0 (feature bit `0x40`): the settings in RAM differ from flash (`config_unsaved()`), so the app knows the true saved state after an app restart, a USB reconnect, an OLED edit or a slot switch (which saves); and byte [25] (when wLength ≥ 26): the player indicator LEDs the host set (bits 0..4); [26] model (0 DualSense, 1 Edge) and [27..28] colorway code, ASCII, from the factory serial (when wLength ≥ 29; zero until `controller_info_task()` has read it ~1.5–3.5 s after connect (on an Edge after the profile fetch, ~5–7 s), so a previous controller's model never shows; the cached `0x81` reply holding the full serial is dropped right after, and the read is only built with `ENABLE_COMPANION_VENDOR`); and `0xF0` live input (vendor interface only, GET, feature bit `0x20`): the controller's raw input report (USB report 0x01 without the id, before remapping, 63 bytes; zeros without a controller), polled ~30 Hz by the app's live controller view. It's a plain copy of `interrupt_in_data` in the same core-0 context as the Bluetooth writer, so it's consistent and cheap; keep it free of `printf` and flash access. Protocol 1.7 adds the board's name: identity [29] bit 3, then [30..45] (when wLength ≥ 46) ASCII, NUL-padded, from `DS5_BOARD_NAME` (CMake: "Pico 2 W" for `pico2_w`, "Pico W" for `pico_w`, else the `PICO_BOARD` id; 16 characters max, a `static_assert`), so the app names the hardware without an update for each new board. Protocol 1.9 adds remapping the DualSense Edge's extra buttons (identity [29] bit 5): four more remap entries in the remap flash struct after the table (`RemapData.extra`: Fn left, Fn right, left paddle, right paddle = input report byte 9 bits 0x10/0x20/0x40/0x80 without the report id, per SDL_hidapi_ps5.c and daidr/dualsense-tester); each is a standard button 0..15, 0xFE nothing, or 0xFF itself (the default, and what erased flash / older saves read as). `remap_apply` presses the target and clears the source bit, so the game sees only the chosen button. Read with GET 0xED (vendor interface only: ['R','X',1, rev lo, rev hi, 4 entries]); set with 0xF6 func `0x13` ['R','X',1, 4 entries, temporary 0/1]. The 0xF7 config GET is already 63 bytes (body + remap block), which is why the extras have their own read; old apps never see them. Temporary extras share the temporary-remap state: `0x12`, a reboot or a saved `0x10` ends them; saving extras while a game's table is temporary writes the saved table, never the temporary one. Protocol 1.10 adds stick response curves (identity [29] bit 6; [19] bit 2 = temporary curves are on): per pairing slot a curve for each stick, stored after the calibration bodies in the calibration sector (see Flash layout) and applied in `calib_apply` right after the stick calibration step, so on the outgoing host report only, never `interrupt_in_data`. A curve is 9 bytes [type, p1x,p1y, p2x,p2y, p3x,p3y, p4x,p4y]: 0 Linear (identity, skipped; the default, and what erased flash, older saves and any invalid curve read as), 1 Precise (y = x^1.8), 2 Steady (x^1.35), 3 Aggressive (x^0.6), 4 Digital (x^0.3), 5 Custom (piecewise linear through (0,0), the four points, (255,255); x and y non-decreasing, equal x = a step). Presets ignore the points but keep them (the app parks its last custom points there). The math is pure integer in `src/stick_curve.h` (no SDK, compiles on a PC): each half-axis normalized to its reach (127/128) in Q12, radial tilt by integer sqrt, the curve on the tilt (presets are 33-entry tables of round(4096·(i/32)^g), linearly interpolated, so no `pow` runs), direction kept, tilt at or past full (square-gate corners) left alone. The app's `src/protocol/stickCurve.ts` is the same arithmetic step for step and its tests hold sample bytes computed from this header; change both together. Read with GET 0xEC (vendor interface only): ['C','V', 1, slot, flags (bit0 temporary on), saved L, saved R, active L, active R] (41 bytes, the slot in use now). Set with 0xF6 func `0x14` ['C','V', 1, slot, left (9), right (9), temporary 0/1]: saved = written to the calibration sector at once (a temporary pair is never saved: it lives in separate RAM, and a saved set ends it); temporary = a game's profile, RAM only, for that slot, ended by `0x12` (which now also reverts the curves), a reboot or a saved `0x14`. Protocol 1.8 adds temporary remaps (identity [29] bit 4): 0xF6 func `0x11` takes the same framing as `0x10` (['R','M',ver, 16-byte table]) but applies it in RAM only (`remap_set_temporary`, never flash: a game's button layout while it runs, so starting and stopping games doesn't rewrite flash); `0x12` (`remap_revert`) goes back to the table saved in flash, as does a reboot; a normal `0x10` set saves and ends the temporary state. Identity [19] bit 1 = a temporary table is active. Protocol 1.6 adds the right grip's haptics strength: `Config_body.haptics_gain_right` (float [1,6], after `narrator_voice`, so the body is 42 bytes; NaN / out of range takes `haptics_gain`, so older configs keep one strength for both); `haptics_gain` is the left grip. A host config write (0x01) never changes `narrator_voice` (`set_config` keeps it), so a 42-byte body is safe; the app sends 42 bytes only to 1.6+ (older firmware would take byte 37 as the narrator). The remap block in the config GET follows the whole body (offset 42 on 1.6). The OLED Settings menu has separate Hap Left and Hap Right items; each adjusts only its own grip. Classic rumble follows the same strengths: the host 0x02 forward scales SetStateData [2] (right, light motor) by `haptics_gain_right` and [3] (left, heavy) by `haptics_gain` (`scale_rumble` in main.cpp). 0xF6 func `0x0E [side]` (0 left, 1 right, 2 both; identity [29] bit 2) is the app's grip test (haptic feedback test): deferred to cmd_task, it plays a dongle-generated HD haptics wave on the chosen grip(s) at each grip's strength, 0.5 s here (protocol 1.15 adds a duration byte; the wave itself is described there). Protocol 1.5 adds calibration (identity [29] bit 1): `src/calib.{h,cpp}`, **one CalibBody per pairing slot** in its own flash sector (`CALIB_FLASH_OFFSET`, 4 sectors below the BT bank), the current slot's applied in `main.cpp` to the outgoing host report copy right before `remap_apply`, never to `interrupt_in_data`; each part is skipped while it is identity. Sticks [0..3]: center offset, then each half-axis normalized to its own reach (`min(outer, 127-c)` / `min(outer, 128+c)`), a radial deadzone, full tilt at 0 and 255 (the app's `correctStick` matches). Triggers [4,5]: lo..hi stretched to 0..255. Gyro int16 at [15,17,19] (pitch, yaw, roll): the body stores the raw rest reading; hosts already subtract the factory bias from feature report 0x05, so the dongle subtracts only `rest - factory bias` (`calib_service()` in the main loop reads 0x05 per connection; an implausible factory cal, |bias| > 1024, counts as 0 like SDL); gyro is left alone until 0x05 has arrived. Set: 0xF6 func 0x0D ['C','L',ver(2), slot, 18-byte CalibBody], validated (center ±40, deadzone ≤64 < outer 64..128, trigger hi-lo ≥64) and saved at once; it doesn't bump the host config generation. Get: 0xEE (vendor interface only) = [current slot] + that slot's body. Protocol 1.4 adds identity [29] (when wLength ≥ 30), a second feature byte: bit 0 = `0xEF` OLED screen mirror (vendor interface only, GET, 1028 bytes in one control transfer, the only reply longer than 63 bytes; handled in `vendor_itf.cpp` before the generic path): [0] power state 0 on / 1 dimmed / 2 off, [1] current screen, [2] contrast, [3] frame counter, then the 128×64 image as last flushed (`fb_shown`, copied in `flush_fb_raw()`), row-major, 16 bytes per row, MSB = leftmost pixel. Main-loop only like `fb`, so no locking. `0xF6` functions: `0x01` config to RAM, `0x02` save, `0x03` USB reconnect, `0x04`/`0x05` switch/forget slot, `0x06` wipe slots, `0x07` reboot, `0x08` BOOTSEL, `0x09` factory reset, `0x0A` trigger preset preview, `0x0B [v]` narrator (protocol 1.3, feature bit `0x80`: config byte 37 `narrator_voice`, 0xFF off or 1..7 = en de fr es pt-BR zh-CN ja; deferred, saved by `config_save_narrator()` on its own so it never saves other unsaved edits), `0x0C [line][lang]` say a narrator line now (preview), `0x10` remap, `0x11` remap for now (RAM only), `0x12` back to the saved remap (and the saved stick curves, proto 1.10), `0x13` Edge extra buttons, `0x14` stick response curves, `0x15` reset the timings (proto 1.11). Only SETs to `0xF6` run functions (the other ids are read-only). Save, slot, reboot, BOOTSEL, reset and trigger preview are deferred to `cmd_task()` in the main loop (reboot/BOOTSEL 50 ms later so the host gets its ACK); poll `0xF1` until the result leaves `PENDING`. While one is pending every SET answers `BUSY`, and the deferred result is reported under its own function id. The active slot changes only through `0x04`: a `0x01` config write and a factory reset (`0x09`) keep `current_slot`. Windows caches "no MS OS descriptor" per VID/PID/bcdDevice (`HKLM\SYSTEM\CurrentControlSet\Control\usbflags\054C0CE60100\osvc`): on a PC that once had a real DualSense on USB, WinUSB won't bind until that key is deleted. Protocol 1.11 adds per-stage timings (identity [29] bit 7, the last bit of that byte): `0xFC` (CPU telemetry, 11 bytes before) answers 63 bytes when wLength ≥ 63: [11] layout version 1 (bit 7 set = microsecond timer instead of the cycle counter), [12] stage count (8), [13..14] u16 seconds since the last reset (saturating), then per stage i at [15 + 6i] a u32 average in ns and at [19 + 6i] a u16 max in µs (saturating at 65535), stages in order: 0 whole main-loop pass, 1 `cyw43_arch_poll` + BT connection watchdog, 2 `tud_task`, 3 `audio_loop` + `voice_task`, 4 `cmd_task` + `interrupt_loop` + `calib_service`, 5 `oled_loop`, 6 core1 speaker frame (resample + Opus encode), 7 core1 mic frame (decode or concealment). The average is sum/count over the window, both halved when the count reaches 65536 or the sum 2^31 ticks (older samples weigh less); a stage with nothing recorded since the reset reads 0. `0xF6` func `0x15` resets every stage (a generation number: each core zeroes its own stages on their next sample) and is answered at once. Apps before 1.11 ask `0xFC` for 11 bytes and get exactly those. Protocol 1.12 adds controller health & info (identity [46], a third feature byte, when wLength ≥ 47: bit 0; `src/ctrl_info.{h,cpp}`, only with `ENABLE_COMPANION_VENDOR`). GET `0xEB` (vendor interface only, handled in `vendor_itf.cpp` before the generic path) takes a **selector in wValue's high byte** (wValue = sel << 8 | 0xEB), so every reply stays within the 63-byte cap: sel `0x00` header (14 bytes) ['C','H', ver 1, state (0 idle, 1 running, 2 done, 3 no answer, 4 controller gone), dev, action, pages received, request number (bumps per accepted 0x16), model (0 DS, 1 Edge, 0xFF unknown), flags (bit0 report 0x20 cached, bit1 0x22 cached), u32 BT patch version from 0x22 [31..34]]; sel `0x01` controller firmware (60 bytes): [0] bit0 valid, [1..59] = cached feature report 0x20 bytes 1..59 at their own offsets (build date/time, fw type, sw series, hw info, main fw, update version [44..45], SBL, DSP, MCU DSP) with the device-info bytes [32..43] zeroed; sel `0x10 + p` (p < 6) result page (59 bytes): [p, state, request number, 56 bytes], zeros unless the request is done and has that page. `0xF6` func `0x16 [dev, action, pages]` queues a Sony test command (0x80 dev/action → 0x81 [0x81, dev, action, status, 56 bytes, crc32] pages): **only** 0x70/1 lifetime counters (1..6 pages) and 0x04/3 battery voltage (1 page, u16 mV) are allowed (INVALID otherwise: no serial reads, no writes), FAILED without a controller, BUSY while one runs; OK = queued, not a deferred function, so other commands aren't blocked. `ctrl_test_task()` (in `cmd_task`) sends it only after the colorway read is Done and while the Edge profile module isn't using the slot (they share the controller's single 0x80/0x81 slot), polls GET 0x81 one request at a time (a reply is dropped from the cache once taken; re-ask after 150 ms of silence; 3 s overall → NO_ANSWER), and ends a paged block at status 2, at the page limit, or when the controller stops echoing dev/action. The counters block starts with a status byte; the controller serial (block [1..17]) and on the Edge the stick-module serials ([183..199], [220..236]) are blanked when the block completes, and a disconnect clears everything (state back to idle). Counter offsets and the firmware-version gate (main fw update version > 1106, Edge > 374) follow daidr/dualsense-tester (MIT); the app parses them. Protocol 1.13 adds upstream's settings batch (identity [46] bit 1): seven `Config_body` fields after `haptics_gain_right` (body 49 bytes; `kConfigBodyV16` = 42 marks where they start): `trigger_reduce` [0,10], `speaker_gain` [0,7] (0 = the game's own for both), `lock_volume`, `mic_select` (0 auto, 1 built-in, 2 headset), `speaker_select` (0 auto, 1 speaker, 2 headset, 3 off), `status_gpio_pin` (0xFF off or a pin `status_gpio_pin_valid()` accepts, `src/status_gpio.h`) and `status_gpio_mode` (0 high while connected, 1 a 200 ms pulse on connect). **The 0xF7 config GET is capped at 63 bytes and the 1.6 body + remap block already filled it**, so a GET of ≥ 63 bytes still answers the first 42 body bytes with the remap block at 42 (every app reads the remap from there), and a shorter GET answers the whole body (apps from 1.13 ask for `sizeof(Config_body)`; older ones ask for ≤ 42 and never see the new fields). A config write (0x01) of 49 bytes sets them; an older app's 42-byte write leaves them alone. The pure stamping logic is `src/state_override.h` (host-tested): on every forwarded host 0x02 report (`state_stamp_config(ss, true)`), a non-zero `trigger_reduce` forces MotorPowerLevel's high nibble (keeping the rumble nibble the game last set), a non-zero `speaker_gain` forces SpeakerCompPreGain, a non-zero `mic_select` forces MicSelect (keeping NoiseCancelEnable, which the speaker needs), and `lock_volume` clears the game's volume / mic volume / audio mute / mute light allow bits; with all at 0 the game's report goes out untouched (upstream's #228 was the dongle re-sending a latched state). The connect-time state (`bt_send_state`) is stamped too (its mic choice is always the setting's), and `state_config_task()` (main loop, once USB is up) pushes a changed setting at once (back to 0 puts back the game's last value), and keeps the mute light on while the controller's mic is muted (input [53] bit 2). `status_gpio_task()` (main loop) drives the pin. Protocol 1.14 adds the PC sleep options (identity [46] bit 2, `src/usb_power.h`): [47] (when wLength ≥ 48) = `Config::power_flags` (bit 0 controller off once the PC has slept 3 s, default on; bit 1 PS wakes the PC, default off; 0 when [46] bit 2 is clear); set with 0xF6 func `0x17 [bits]` (deferred, saved on its own like the narrator; INVALID for other bits). They live after `Config_body` in the config page, outside the CRC (0xFF from older firmware reads as the default), so they never ride on a body write and need no room in the 63-byte 0xF7 GET. A change to bit 1 shows in the configuration descriptor at the next enumeration. Protocol 1.15 adds the timed grip test (identity [46] bit 3): 0xF6 func `0x0E [side, tenths]`, the second byte optional (absent = 0.5 s, what apps before 1.15 send; 0 = stop; else clamped to 1..50 = 0.1–5 s). Since 8c6a981 the test is HD haptics, not classic rumble: `src/grip_wave.h` (pure, host-tested in `tests/host/test_grip_wave.cpp`) generates a 125 Hz square wave (period 24 samples) in the controller's 3 kHz haptic sample stream, on the chosen grip(s) only, level 0.25 through the host haptics' gain math (`haptic_to_s8`) with each grip's strength (`haptics_gain` left, `haptics_gain_right` right: 1 = a quarter of full scale, 4 and up full), exactly tenths x 300 samples, then silence. It goes out in the 0x39 audio report's haptic block (`audio.cpp`, `audio_grip_test_start/stop`): while the host streams audio, `audio_loop` puts the wave in place of the host's / Audio Auto Haptics samples at the decimation point; with no host audio, `grip_test_task()` (in `audio_loop`, RAM-resident) sends the dongle's own 0x39 reports, 64 sample pairs each every 64/3000 s (`GripReportClock`: the host haptics' packet rate, two at once as a head start, resync after a stall), carrying the narrator's frames if she is speaking (`voice_task` sends none of its own meanwhile), and one silent report at the end. A new `0x0E` replaces the running test (side and time) keeping the wave's phase, so there is no gap; a stop with nothing running is OK and sends nothing; a BT disconnect ends it. The game's classic rumble is never touched by the test. The app sends one `[side, 30]` per press (3 s) and `[side, 0]` to stop; with older firmware it repeats the 0.5 s pulse every 0.4 s. Protocol 1.16 adds the controller's mic level (identity [46] bit 4): `Config_body.mic_level` at byte 49 (body 50 bytes; a 1.13–1.15 app's 49-byte GET and write never reach it, so they leave it alone, and a body saved by older firmware reads 0xFF there, which takes the default). 0 = follow the PC (default; the USB mic feature unit's 0..48 dB as VolumeMic 0..0x40, `usb.cpp`), 1..64 (`kMicLevelMax`) = SetStateData VolumeMic forced to that value. VolumeMic is the controller's only mic level (absolute and non-linear, topping out at 0x40), so the setting replaces the PC's level rather than combining with it. `state_set_mic_volume()` keeps the PC's level in `state[]` but sends it only while the setting is 0; `stamp_overrides` replaces the level in any report that has AllowMicVolume set (a game's, the connect-time state) and adds the bit to none; `build_override_push(..., level, pc_mic)` sends a change at once, back to the PC's level at 0. Identity [48] (when wLength ≥ 49) is the PC's mic volume as VolumeMic (`state_get_pc_mic_volume()`, 0x40 until the PC sets one), so the app can warn that following the PC means a silent mic: Linux's DualSense UCM names no capture mixer element, so PipeWire uses software volume and the boot-time ALSA restore (often `Headset Capture Volume` 0) stays on the hardware control. The OLED Settings item is `Mic Lvl` (PC or 1..64, ±4 per press). Protocol 1.17 adds the controller's mic echo cancellation (identity [46] bit 5): `Config_body.mic_echo_cancel` at byte 50 (body 51 bytes; a 1.16 app's 50-byte GET and write never reach it; 0xFF from older firmware takes the default, 1). 1 = on (default): `stamp_overrides` sets AudioControl [7] bit 2 (EchoCancelEnable, `kAudioEchoCancel`) in any report with AllowAudioControl (a game's, Linux hid-playstation's 0x00/0x30 on a headset plug/unplug, the connect-time state) and adds the section to none; 0 = the game's own bit. A change is pushed at once with the mic choice's AudioControl push (`build_override_push`'s `mic`, which now applies both). OLED Settings item `Echo Cancel` (on/off). NoiseCancelEnable (AudioControl bit 3, `kAudioNoiseCancel`) has no setting: `stamp_overrides` and `build_override_push` set it in every report that sets AudioControl, a game's included, because clearing it halves the speaker (upstream b821623, #263) and Linux hid-playstation sends AudioControl 0 / 0x30 on every headset plug/unplug. A game's explicit off can't be told from that zero; SDL never sets AllowAudioControl and upstream forces the bit wherever it sets AudioControl, so there is no known game to break. Don't add an opt-out without a game that needs one. Protocol 1.18 adds remote KEY0 / KEY1 presses (identity [46] bit 6): 0xF6 func `0x18 [key, press]` (key 0 KEY0, 1 KEY1; press 0 short, 1 long; INVALID for anything else or a missing byte), deferred to `cmd_task()`, which queues it with `oled_key_inject()` (OK; BUSY when four presses already wait). The press logic is `src/oled_keys.h` (pure, host-tested in `tests/host/test_oled_keys.cpp`): `oledkeys::step()` is what `handle_buttons()` runs for the board's keys (debounce, short/long, the KEY0+KEY1 reboot chord), and the injector holds a virtual key down (60 ms short, long-press time + 0.1 s long, 60 ms up between queued presses) that `handle_buttons()` ORs with the pin. So a remote press debounces, wakes the screen and navigates exactly like a finger (KEY0 next screen, short or long; KEY1 short back, long brightness cycle + save), with or without an OLED wired; the app sees the result in the 0xEF mirror. Protocol 1.19 adds virtual controller buttons for the OLED screens (identity [46] bit 7, the last bit of that byte): 0xF6 func `0x19 [button, hold ms lo, hold ms hi]` (button 0 up, 1 down, 2 left, 3 right, 4 △, 5 ○, 6 ✕, 7 □, 8 R1; hold 0 or left out = a 100 ms tap, up to 5000 ms; INVALID for another button or a longer hold), deferred to `cmd_task()`, which queues it with `oled_pad_inject()` (OK; BUSY when four presses already wait). The logic is `src/oled_vpad.h` (pure, host-tested in `tests/host/test_oled_vpad.cpp`): `vpad_tick()` (every `oled_loop` pass, before `screen_input_tick()`) holds the button down for the asked time and lets go (60 ms up between queued presses, so each is an edge), and `g_in` = the controller's input bytes 7/8 (only while one is linked) with the virtual button merged in (a D-pad direction replaces the hat, face buttons and R1 add) is what every screen's input handler reads instead of `interrupt_in_data`. **Nothing writes `interrupt_in_data` or the host report, so games never see these presses** (and the PS+Mute reboot combo in `main.cpp` can't be triggered this way). A press wakes the screen (always, whatever CtrlWake says) and starts once the panel is on (at most 1 s later), so a tap on a dimmed screen acts instead of only waking it. Without a controller the Settings, Slots and Diagnostics screens take virtual presses; Lightbar and Trigger Test still need one (their actions drive the controller's lightbar and triggers). The Lightbar favorite save (△ ○ ✕ □) moved from its 10 Hz render into `lightbar_handle_input()` (every pass, like R1) so a short tap can't fall between frames. What the screens react to: Settings D-pad ▲▼ select (wraps), ◀▶ adjust, △ release = save, △ held 2 s on Reset to defaults / Wipe all slots; Slots ▲▼ cursor, △ switch to the cursor slot, □ held 1.5 s forget it; Lightbar R1 next mode, △ ○ ✕ □ save the current color to favorite 0..3; Trigger Test △ next preset; Diagnostics ▲▼ scroll. Bump `PICO_PROTO_MINOR` for additions, `MAJOR` for layout breaks (the app refuses a major mismatch). Host config writes bump the generation counter and `oled.cpp:sync_host_config_changes()` re-reads the lightbar, brightness and Settings snapshot, so a dongle-side △ save can't write a stale copy over the host's changes.
- Narrator (firmware lines) → `src/voice.cpp`. Her connected / slot / battery-low lines are pre-encoded Opus in `src/voice_bank.bin` (`tools/build_voice_bank.py`, from the app repo's mastered `assets-src/voice/<lang>-speaker/fw_*.wav`), `.incbin`'d into flash (~600 KB). Nothing is decoded or encoded: while a line plays its frames replace the host's speaker frames in the `0x39` report (padded to 200 bytes with `opus_packet_pad`), and with no host audio flowing `voice_task()` sends `audio_send_voice_report()` itself at the controller's rate (one per 21.33 ms, `src/report_clock.h`), with ~300 ms of silent frames before a line and 85 ms after on a cold path. The connected line starts when the path is ready, at 2.5 s after the link at the latest (`src/voice_cue.h`). A slot switch while connected plays the slot line, then drops the controller (`voice_disconnect_after_line`). Off until the app turns her on.
- Audio / haptic path → `src/audio.cpp` (the haptics' 48k→3k step is `src/haptics_decimate.h`, inlined into the RAM-resident `audio_loop`). **Don't** add stack arrays sized smaller than the resampler / Opus expects (this is the C1 bug that caused the long-standing "audio stuttering" issue — fix landed in upstream `5b04cbd`, but the lesson stands).

## Don't do these

- **Don't disable the watchdog** without explicit user authorization. `watchdog_enable(1000, true)` in `src/main.cpp:main()` is the safety net for hangs.
- **Don't add fallbacks for missing OLED** beyond what `oled.cpp` already does (no init checks, SPI writes harmlessly to nothing) — the firmware must boot identically with or without the display.
- **Don't write a new flash sector backend** without updating the `static_assert(SECTOR_OFFSET % FLASH_SECTOR_SIZE == 0)` pattern from `slots.cpp` and confirming no overlap with `config.cpp`'s sector.
- **Don't push to `upstream` or `upstream-fork`** by accident — only `origin/master` is the personal fork's deployment target.
